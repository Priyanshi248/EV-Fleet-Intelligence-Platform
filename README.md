# EV Fleet Intelligence Platform

An AI-assisted, machine-learning-enabled platform for monitoring electric vehicle fleets, analysing battery health, supporting predictive maintenance and procurement decisions, assessing supply-chain risks, and tracking emissions-reduction scenarios.

**Technology:** Next.js · React · FastAPI · Python · PostgreSQL · SQLAlchemy · scikit-learn · Docker Compose · GitHub Actions · OpenRouter

> **Project scope:** The repository includes simulated and demonstration fleet/battery data. It is a prototype and decision-support project, not a live vehicle-telematics system or a safety-certified battery-management product.

## Overview

EV Fleet Intelligence Platform brings fleet operations, battery analytics, maintenance information, procurement, supply-chain information and sustainability scenarios into one web application. The Next.js frontend calls a FastAPI backend. The backend reads and writes application records in PostgreSQL and exposes the Battery ML inference service. The AI assistant retrieves platform context and can use OpenRouter to generate natural-language answers.

### Objectives

- Provide a consolidated view of vehicles, status, telemetry and charging sessions.
- Estimate battery State of Health (SOH) and Remaining Useful Life (RUL) from the supplied demonstration data.
- Present vehicle-specific battery degradation and risk analysis.
- Support EV procurement and recommendation workflows.
- Present supplier, battery-material and supply-chain assessment information.
- Create and review emissions-reduction scenarios.
- Make platform information accessible through a conversational assistant.
- Demonstrate containerization, automated tests and CI image/build validation.

## Platform modules

### Dashboard and fleet management

Fleet summary, vehicle records, status information, telemetry and charging-session views.

### Battery intelligence

Vehicle-specific predicted and measured SOH, RUL estimates, degradation history/forecast, battery operating parameters and model-based risk information.

### Predictive maintenance

Maintenance alerts, severity/status information, risk details and recommended actions where available in the underlying records and model output.

### EV procurement

EV catalogue, procurement requirements, recommendations and recommendation history.

### Supply-chain intelligence

Supplier records, battery materials, supplier-risk assessments and summary information.

### Net-zero and sustainability

Baseline/projected emissions and saved emissions-reduction scenarios.

### AI assistant

Conversational questions about fleet, battery, maintenance, charging, procurement, supply chain and Net-Zero data. Battery-health answers use the shared Battery ML service so that assistant results align with the battery API. OpenRouter is the configured external model provider; a database-grounded fallback is available if the provider is unavailable or not configured.

### ML performance

Displays model evaluation information generated by the Battery ML pipeline.

## Run with Docker

### Prerequisites

- Git
- Docker Desktop with Docker Compose

### 1. Clone the repository

```bash
git clone https://github.com/Priyanshi248/EV-Fleet-Intelligence-Platform.git
cd EV-Fleet-Intelligence-Platform
```

### 2. Create the environment file

In PowerShell:

```powershell
Copy-Item .env.example .env
```

Edit `.env` and provide the required database and AI settings. See [Environment configuration](#environment-configuration). Do not commit `.env`.

### 3. Build and start the services

```bash
docker compose up -d --build
```

Check service state:

```bash
docker compose ps
```

### 4. Open the application

| Component | Address |
|---|---|
| Web application | http://localhost:3000 |
| Backend health | http://localhost:8000/health |
| Swagger / OpenAPI UI | http://localhost:8000/docs |
| ReDoc | http://localhost:8000/redoc |

## Environment configuration

The root `.env` file is loaded by Docker Compose and injected into the backend container. Configure the values required by your `docker-compose.yml` and application settings. The currently used setup includes:

```dotenv
POSTGRES_PASSWORD=replace_with_a_strong_password
DATABASE_URL=postgresql+psycopg://ev_admin:URL_ENCODED_PASSWORD@localhost:5432/ev_fleet
DATABASE_URL_DOCKER=postgresql+psycopg://ev_admin:URL_ENCODED_PASSWORD@postgres:5432/ev_fleet
OPENROUTER_API_KEY=replace_with_your_key
OPENROUTER_MODEL=openai/gpt-4o-mini
```

Use the same PostgreSQL credentials in the connection strings and URL-encode special characters in the password. The host differs by execution context: `localhost` is for a process on the host machine; `postgres` is the Compose service name used by the backend container.

The frontend image receives `NEXT_PUBLIC_API_URL` at build time. For a browser connecting to a locally published backend, the expected value is `http://localhost:8000`. Do not put the OpenRouter key in a `NEXT_PUBLIC_` variable or in frontend code.

If your `.env.example` specifies additional required variables, retain and configure them too. Never commit real credentials or share the contents of `.env`.

## Database migrations and sample data

Apply Alembic migrations from the backend container:

```bash
docker compose exec backend alembic upgrade head
```

Check the current revision:

```bash
docker compose exec backend alembic current
```

The earlier project README referenced a sample-data command `python -m scripts.seed_data`. Verify that `scripts/seed_data.py` exists in your checkout before using that command. Run a seed script only once on a fresh database unless its implementation explicitly supports safe repeated execution. Do not remove the `postgres_data` volume to troubleshoot ordinary application issues.

## Local development

The Docker Compose setup is the recommended path for running all three services together. For separate local development, install backend dependencies in a virtual environment and frontend dependencies in the `frontend` directory.

Backend:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
uvicorn app.main:app --reload
```

Frontend (in a second terminal):

```powershell
Set-Location frontend
npm ci
npm run dev
```

Ensure the frontend's local environment points to `http://localhost:8000` and the backend's `DATABASE_URL` points to a reachable PostgreSQL instance.

## Battery ML component

The `battery_ml/` package provides battery data preparation, feature engineering, model training/evaluation and inference logic. The serialized model bundle is stored at `battery_ml/models/battery_models.joblib`. Processed data and reports are under `battery_ml/data/processed/` and `battery_ml/reports/`.

The vehicle-health response includes information such as predicted SOH, measured SOH, RUL, degradation history/forecast, model input snapshot and risk assessment for the available demo vehicle IDs.

Typical workflow scripts:

```bash
python -m battery_ml.clean
python -m battery_ml.train
```

Run training only when intentionally regenerating the model bundle. The runtime service expects the trained model and its supporting dataset files to be present.

## AI assistant

The assistant endpoint accepts a chat message and retrieves relevant platform context from the application database. For battery-health questions it calls the same Battery ML service used by the vehicle-health endpoint, so the assistant's battery figures are aligned with that service rather than stale historical prediction rows.

Example request:

```bash
curl -X POST http://localhost:8000/api/v1/assistant/chat \
  -H "Content-Type: application/json" \
  -d '{"message":"Summarize the current EV fleet status."}'
```

OpenRouter requires a backend-side API key. If the external provider cannot be used, the backend can return a deterministic database-grounded fallback for supported query categories.

## Testing

Install development dependencies:

```bash
python -m pip install -r requirements-dev.txt
```

Run the automated tests from the repository root:

```bash
python -m pytest -q
```

The current test suite includes Battery ML checks for valid vehicle-health outputs, vehicle-specific values and unknown vehicle IDs.

The backend API was also manually smoke-tested during development across health, dashboard, fleet, maintenance, ML, three demo battery vehicles, procurement, supply-chain and Net-Zero read endpoints. Manual smoke checks are not a substitute for automated integration tests.

## Continuous integration

GitHub Actions workflow: `.github/workflows/ci.yml`.

It runs on pushes, pull requests and manual dispatch, with three jobs:

1. **Backend automated tests** — installs Python dependencies and runs Pytest.
2. **Frontend production build** — installs Node dependencies with `npm ci` and runs `npm run build`.
3. **Docker image validation** — builds the backend and frontend images after the first two jobs succeed.

See the repository's **Actions** tab for the status and logs of each workflow run.

## Useful Docker commands

```bash
# Start existing containers
docker compose start

# Stop containers without deleting persistent data
docker compose stop

# View service status
docker compose ps

# Follow backend logs
docker compose logs -f backend

# Follow frontend logs
docker compose logs -f frontend

# Follow PostgreSQL logs
docker compose logs -f postgres

# Rebuild and start after code changes
docker compose up -d --build

# Stop and remove containers/networks (keeps named volumes)
docker compose down
```

**Warning:** `docker compose down -v` deletes named volumes, including the PostgreSQL data volume. Do not use it unless you intentionally want to erase the persisted database.

## Security notes

- Keep `.env` and `frontend/.env.local` out of version control.
- Keep OpenRouter credentials on the backend only; never expose them through `NEXT_PUBLIC_` variables.
- Use strong database credentials and protect deployment secrets.
- Use HTTPS, access control and managed secret storage for any public deployment.
- Treat the included datasets and model as project demonstration assets.

## Limitations and future work

The current repository is a local/containerized prototype. Real-time telemetry requires integration with vehicle hardware or an external telematics provider. Production use would also require authentication/authorization, operational monitoring, deployment hardening, stronger automated API/database integration coverage, and validation against representative real-world fleet data. Model performance and risk outputs should be evaluated before any safety-critical or operational decision is based on them.

Potential extensions include real-time telemetry ingestion, role-based access, audit logging, model drift monitoring/retraining, broader optimization methods, richer integration tests and cloud deployment.
